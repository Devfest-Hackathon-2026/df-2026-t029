## 第2回: どうすればもっとよくなるか（6人、テーマは維持）

### 「Gemini アプリで十分では？」への答え（全体の軸）

> Gemini アプリの抽出は一度きりで状態が残らない。このアプリは**抽出結果を状態として持ち続け、当落や告知の変更で再計算し、同じ推しのファンと共有する**。

### 各担当のイチオシ

| 担当 | イチオシ | 中身 |
|---|---|---|
| AI 体験 | **受付チェーン＋相対期限の保持** | responseSchema の各ステップに `type`(enum) / `absoluteAt` / `relativeTo` / `offset` / `appliesTo` / `evidence` / `confidence`。「当落発表後3日以内」は Gemini に日時を決めさせず保存し、「当選」押下時にコードで確定日時を計算 |
| 共通データ | **差分マージ＋変更速報** | 既存と違う値は根拠付き proposal に。複数人一致で「確認済」→確定値に昇格。変更前後をカードで全フォロワーに表示（例: 入金期限 11/20→11/18、3人確認） |
| 当事者兼 UX | **入力口を1つに＋1タップ当落** | スクショも FC メール本文も同じ抽出処理へ。ホーム最上段に「次の締切まで◯時間」と今日やること3件、各カードに状況ボタン |
| 社会課題 | **取り逃した瞬間に公式の次の手** | 「落選」や入金期限切れで、公式リセール・一般発売・追加公演を提示し、SNS 個人間譲渡の注意を一文。「取り逃し→非公式譲渡→詐欺」の連鎖を断つ |
| デモ演出 | **告知が変わった瞬間** | 架空公式サイトに変更告知 → A が読み込ませる → 差分提案 → B の画面に差分カード（分割画面ワンテイク）→ B が落選を押して締切が組み替わる |
| スコープ管理 | コアを深くし、周辺は切る | 下記の「切るもの」と日別マイルストーン |

### 補足案

- 確信度の低い項目を黄色の「要確認」に。斜め撮りなど意地悪な画像で実演すると誠実さが伝わる。
- 根拠を画像上の枠（box_2d）でハイライト。座標精度は未検証なので、駄目なら原文の引用表示。
- 文脈付き抽出: その推しの既存共通データ（数件）を渡し、`relation`（new / 続報 / 変更 / 重複）と `matchedEventId` を返させる。自動確定はせず候補提示。
- 「あなたの登録で◯人の締切が埋まりました」表示（作るのは簡単だが見せかけになりやすい）。
- 匿名集計「フォロワーの6割が申込済」: 分母10人未満は非表示、当選・入金率は出さない（転売相場への影響）。
- 推し色テーマ（`ColorScheme.fromSeed`）。半日でできるが優先度は最後。
- 配慮申告期限を抽出項目に1つ足す（スライド1行程度にとどめる）。
- 汎用性（奨学金・インターン締切）はピッチ最後の一言だけ。画面には入れない。
- 視覚障害者への言及は避ける（Flutter Web の読み上げ対応が弱く突かれる）。

### 切るもの（スコープ管理の提案）

- P2/P3 すべて、チャット、複数カレンダー対応、凝った変更履歴 UI。
- FCM 予約通知 → アプリ内の締切順表示＋カレンダー側のリマインダーで代替（余裕があれば4日目）。
- Calendar API → 「Google カレンダーに追加」リンク（TEMPLATE URL）。共通データ変更時に自動更新されない点は判断ログに「捨てた案と理由」として書く。
- 推しの手動承認 UI → 誰でも作成可＋名前正規化で重複警告。承認制は status フィールドで将来対応と設計に書く。
- function calling / エージェントのループ → 文脈を最初から渡す方式で代替。
- Web Share Target（共有シート受け取り）→ Android Chrome の PWA のみ、iOS 非対応。余力があれば。

### まだ割れている点（提案のみ）

- **Gemini 呼び出し**:
  - AI 体験担当 → Cloud Functions（読み込み・出力検証・提案書き込みをサーバーでまとめ、安全性を説明しやすい）。
  - スコープ管理担当 → Firebase AI Logic（Vertex AI バックエンド）＋App Check。共通データの保護は Firestore ルール（直接上書き禁止、proposals の create のみ許可）で担保。Functions は Dart で書けずデバッグが重い。
- **「確認済」昇格のしきい値**: 3人一致だとデモ規模では届かない → フォロワー数に応じて可変（最低2人、または5%）。

### Firestore ルールの方向性（提案）

- 推しマスタ: クライアント書き込み禁止（または status 付きで作成のみ）。
- events: クライアントからの update 禁止。`proposals` の create のみ許可（`uid == request.auth.uid`）。
- 変更履歴: create のみ（update/delete 不可）、`changedBy == request.auth.uid` 必須。
- 荒らし対策: フォロー済み、提案は1日10件まで、採用率の低いユーザーの提案は表示順を下げる。
- 集計 `aggregates/{eventId}`: サーバー書き込み・クライアント読み取り専用。
