## 2026-11-05 Riverpod の自動の再試行は、permission-denied のときだけ止める
- 決めたこと: `allOshisProvider` と `followStateProvider` では、Firestore の `permission-denied` のときは再試行しない。それ以外のエラーは、Riverpod 3 の既定（`ProviderContainer.defaultRetry`。最大10回、200ms〜6.4秒の指数バックオフ）に任せる。
- 経緯: ui が U5 の確認中に気づいた。Riverpod 3 は、失敗したプロバイダを既定で再試行する。そのため、ルールで拒否された読み取りも10回繰り返していた。
- 比べた案: (1) 権限エラーのときだけ止める (2) 再試行をすべて止める（`retry: (_, _) => null`） (3) 既定のまま
- 選んだ理由: 権限エラーは何度読み直しても結果が変わらず、読み取り回数が無駄に増えるだけ。一方、一時的なネットワーク障害は、再試行で自然に直る。
- 捨てた案と理由: (2) 通信が一瞬切れただけでもエラー表示になる。(3) 権限エラーのたびに、無駄な読み取りが最大10回起きる。
- AI の関わり方: ui エージェントが、実際に動かしたテストで気づいて報告した。リーダーが Riverpod のソース（`defaultRetry`）を読んで既定の動きを確かめ、決めた。
- 決めた人: リーダー（Claude）。ユーザーへの報告済み

## 2026-11-05 ログイン状態の読み込み中も uid を取る（D6 の修正）
- 決めたこと: `currentUidProvider` は、ログイン状態のストリームが最初の値を流すまで、`FirebaseAuth.currentUser` の uid を使う。`main.dart` がログイン状態の復元を待ってから起動するので、この値は正しい。

- 比べた案: (1) 読み込み中は `currentUser` を使う (2) 読み込み中は何も流さず、読み込み中の表示を続ける（qa の案）
- 選んだ理由: 読み込み中の表示を挟まずに、すぐ一覧を出せる。契約と型が変わらず、画面への影響もない。

- AI の関わり方: qa エージェントがレビューで指摘し、data エージェントが2案を比べて選んだ。
- 決めた人: data エージェント（リーダーが確認）
- 追記（実装後）: data が公開関数 `firestoreRetry` として実装した。Riverpod 3.4.3 では、プロバイダ自身の `retry` がコンテナの `retry` より優先される。そのため、テストでエラー状態を作るときは `permission-denied` の例外を使う（ほかの例外では再試行のタイマーが残る）。
