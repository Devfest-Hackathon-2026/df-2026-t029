# 計画書: ログイン後の画面に「ヘルプシート（案C）」を足す（redesign/after_login への追加）

> 担当A（とし）の作業を、Claude Code の agent team（リーダー＋チームメイト3人。**モデルは Sonnet 5.5**）で実装するための指示書（仕様書を兼ねる）。人間とエージェントの両方が読む。
> 4章はユーザーが渡したデザイン（案C「ヘルプシートタイプ」・`おしあし_案C_ヘルプシート.html`）を Dart（Flutter）で再現するための仕様。「5. 実装前に確かめること」だけが、リーダーがユーザーに聞く項目（どれも推奨案つき）。
> **この計画書のコードは、Flutter がクラウドの環境に無いため、一度もコンパイルしていない。** 写すときは `flutter analyze` で確かめる。
> 書き方は `markdown/feature_before_login_c_plan.md`（紹介ページの作り直し）に合わせた。章の番号も同じ並びにしてある。

## 0. 作業ブランチと前提

- **作業ブランチは `redesign/after_login`**（`origin/redesign/after_login` と同じ位置にいる。2026-11-08 時点）。ブランチの作成・切り替え・pull・push・マージは人間が行う。エージェントはブランチを切り替えない。
- 完成したら、人間が `redesign/after_login` から `dev` へ Pull Request を出す。`origin/dev` には、このブランチに無いコミットが1つある（`81edf17 docs: add_K.mdの追記（完了）`。文書だけ）。PR の前に、人間が `git merge origin/dev` で追いつく。
- 開始前に、リーダーは `git status -sb` で `redesign/after_login` にいて、`origin/redesign/after_login` より遅れていない（`behind` が無い）ことを確かめる。
- **前提（実装済み）**: ログイン後の画面の統合案 v4「ハコ色」（コミット `fdda7ab`。`lib/theme/hako_app_widgets.dart`・`lib/features/shell/app_shell.dart`・各画面。進捗は `notes/after_login_design_進捗.md`）。**今回は、その上に案C のヘルプ機能を足す。v4 の作り直しではない。**
- **ロジックは変えない。** データ（`models`・`repositories`・`services`・Firestore のルール・`pubspec.yaml`）には触らない。足すのは、画面の部品・文言・状態を1つだけ持つプロバイダ（5.1 の推奨案）・日時の書式の関数。
- **Dart（Flutter）で書く。** JavaScript・HTML で画面を作らない（`web/index.html` も触らない）。参照用の HTML は見た目の見本であって、アプリには入れない。
- Firebase は Spark（無料）プランのまま。**デプロイ（`firebase deploy`）・`git push` はしない。**
- 締切: チームの計画では **11/8（今日）の夜に機能を凍結**する。**間に合わなければ、優先度の低いものから落とす**（1章の P3 → P2 の順）。途中の状態を `dev` に入れない。

## 4. 仕様（デザイン）

### 4.0 見本の読み方

- 見本は `markdown/design_after_login_help/oshiashi_C_help_sheet.html`（1ファイル）。**CSS の値が正**。スマホの枠（390×844）は見せるための枠で、アプリには無い。
- 見本の `VARIANT='C'` の分岐だけを見る（`A`・`B` は別案。作らない）。見本にある `guideBlock`・`.guide`・`.sec-desc`（案B）は使わない。
- **px はそのまま論理ピクセルにする。** 書体の太さ 800 は 700 にする（`HakoFonts.jp` は 700 まで）。行の高さは `HakoFonts` の既定（1.75）のままにせず、指定した値（見本の `line-height`）を渡す。
- 見本の色（`--yellow: #F5D31A` など）は、アプリの `BrandColors`（`hall3: #F2D21B` など）と少し違う。**強い色は `BrandColors` を使う**（v4 で決めたとおり）。淡い色だけ、見本の値を足す（4.7）。

- **見本のサンプルの文言が、今のアプリと違う箇所がある**（例: ライブ一覧の「右下の『ライブを追加する』」は、今は区画の下の「ライブを追加」。メンバーの開閉は「メンバー ▼」ではなく丸い矢印）。**文言は 4.10 の表（実際の画面に合わせて直したもの）を正とする。** 見本の文字をそのまま写さない。

### 4.2 「?」ボタン（R1）

- **出す場所**: 幅 720 未満（`kHakoWideBreakpoint` 未満）は、`HakoAppBar` の右（`AccountMenuButton` の左）。幅 720 以上は、左のタブの下側（**アカウントのボタンの上**。5.2）。
- **出す条件**: 今のパスが、`/`・`/oshi`・`/lives`・`/trade`・`/memories` のどれかのとき**だけ**（`helpTopicForPath`。7章）。詳細・追加・編集・プロフィールなど、ほかの画面では出さない。`?tab=` などのクエリは関係ない（`AppShell.location` はクエリを除く）。

- **読み上げ**: ツールチップと `Semantics` のラベルは「この画面でできることを見る」。開いている間は `toggled: true`。
- **押したとき**: 初回の吹き出しを消す（4.4）→ シートを開く（4.3）。
- 上のバーの右の並びは「?」→ アカウント。見た目の間隔はおよそ 10。

### 4.4 初回の吹き出し（R2）

- **出す条件**: 今の画面がホーム（`/`）で、吹き出しがまだ消されていないとき。シートが開いている間は出さない（開くときに消す）。
- **消える条件**: 「わかった」を押す・「?」を押す。ほかの画面に移っても、消えたことにはしない（ホームに戻ると、また出る）。ただし、ホーム以外では出さない。
- **「初回だけ」の覚え方は 5.1**。推奨案は「アプリを開いている間だけ覚える」（次に開いたときは、また出る）。
- **見た目**: 背景 `ink`・文字は白（13・行の高さ 1.55）・余白 10×14・角丸 12・最大幅 230。「?」ボタンを指す三角（幅 16・高さ 8・墨）。中に「わかった」ボタン（背景は白・文字は墨 13・700・角丸 8・余白 4×12・見た目の高さ 32・押せる範囲は 44 以上。上に 8）。
- **位置**: 「?」ボタンの位置に合わせる（`CompositedTransformTarget` / `CompositedTransformFollower` と、`LayerLink` を使う。契約は 7章）。
  - スマホ（幅 720 未満）: 「?」の**下**に出す。三角が「?」の真下を指す（吹き出しの右端が、「?」の中心の右 68 になる。見本の `right:60` ＋三角の半分 8）。「?」との間は 8。

- **文言**（スマホと PC で違う。4.10）。
- `Semantics(liveRegion: true)` で、出たことを読み上げる。

## 10. バグを防ぐための進め方

1. **担当外のファイルは編集しない。** 直してほしい箇所は担当者に SendMessage で伝える。
2. **契約を先に決める。** C1 が終わるまで、`ui-screens` と `qa` は `HakoHint` などに依存する部分を書かない（4章を読み込むのは先に進めてよい）。
3. **各タスクの最初に、方針を3〜5行でリーダーに送る。返事を待たずに書き始める。**（`dev-ui`・`dev-qa` の定義には「返事を待つ」とあるが、**この計画書とチームメイト作成時の指示が優先**する。全員が返事を待って止まるのを避ける。）リーダーは、方針に問題があるときだけ返事をする。タスクを終えたら、完了報告を送ったあと、依存が解けている次のタスクへ**すぐに進む**。
4. **作業ツリーを壊れたまま放置しない。** `ui-core` は C1 でコンパイルが通る薄い部品を先に作り、あとで中身を足す。
5. **品質ゲート:** タスクを完了にするたびに、`.claude/hooks/quality-gate.sh` が動く。失敗すると完了が差し戻される。
6. **見た目は数値で合わせ、見本で確かめる。** 4章の数値と見本の CSS を見比べる。見本の HTML を別のタブで開いて並べて確かめるのは、人間（12章）。Dev Container で画面を撮れるなら撮って比べてよい（撮る道具をリポジトリの依存に足さない。一時ファイルは `/tmp` に置く）。撮れなければ省略する。
7. **実装タスクを終えたら、`qa` にレビューを依頼する。** `qa` はレビュー依頼を最優先で処理する。
8. **共有・ロジックを変えない。** 6章の「読むだけ」のファイルを触らない。
9. **秘密情報を残さない。**
10. **判断を記録する。** 比べた案・選んだ理由・捨てた案は、リーダーが `notes/判断ログ_A.md` に追記する（5章の回答を必ず含める）。

## 14. 使用量の上限で止まったときのために

- リーダーは `notes/after_login_help_進捗.md` を、**タスクが1つ終わるたび**に更新する（状態・担当・触ったファイル・次にやること・ユーザーに聞きたいこと）。止まって再開するときは、まずこのファイルを読み、終わったタスクはやり直さない。
- Claude Code が終了してチームメイトがいなくなったら、まだ終わっていないタスクの担当だけを作り直す（13章の指示に「notes/after_login_help_進捗.md を読み、自分の未完了のタスクから再開すること」を足す）。
- 使用量を抑えるルール（全員）: メッセージは短く、ファイルの中身やテストの出力を丸ごと貼らない。作業中のテストは関係するファイルだけを実行し、全体は完了時の品質ゲートに任せる。長い出力は末尾だけを見る。計画書は自分に関係する章だけを読み直す。進み具合の確認のためだけのメッセージを送り合わない。
- 許可の確認で止まらないように、シェルのコマンドは1つずつ実行する（`;`・`&&`・`|` でつながない、`$変数` を使わない）。ファイルの読み書き・検索は Read・Edit・Grep などの道具を使う。
