## 0. 作業ブランチと前提

- **作業ブランチは `feature/step4.5`。** ブランチの作成・切り替え・pull・push は人間が行う。エージェントはブランチを切り替えない。

## 1. 変更の理由（今の動き）

- 今は、推しをフォローした瞬間に、**誰かが登録したそのすべてのライブ**が自分の「ライブ一覧」とホームの「次の締切」に出る（`followTargetsProvider` → `livesProvider`・`receptionsProvider`）。
- 行かないライブまで並び、締切も増えてしまう。**自分が選んだライブだけ**を一覧と締切に出すように変える。

## 2. 変更後の仕様（ユーザーが決めた内容）

### 2.1 画面の流れ

1. **初めてログインした人**: 最初のページ（ホーム）は今のまま。
2. **推しをフォローしても、ライブ一覧には何も出ない。** ホームの「フォロー中の推し」には、フォローした推しが出る（今のまま）。
3. **ホームの右下のボタン**を「ライブを登録」から **「ライブを追加する」** に変える。
4. 「ライブを追加する」を押すと、**ライブを追加する画面**が開く。
   - グループ（推し）とライブ名を選ぶ・入力すると、**誰かが登録したライブ**が見られる。
   - その中から**自分で選んだものだけ**が、自分のライブ一覧に追加される。
5. ライブを追加する画面の右下に **「ライブを登録する」** ボタンを置く。検索して何も見つからなかったときや、見つかったが追加したいものが無かったときに使う。
   - このボタンの動きは**今までと同じ**（登録方法を選ぶ画面 `/register` → 手入力またはスクショ読み取り → 照合・保存）。

### 2.2 変わらないもの

- 推しの検索・フォロー・追加申請（Step1）
- ライブの登録（手入力・スクショ読み取り）と、照合・更新・変更履歴（Step3・Step4）
- ライブ・公演・受付が共通データであること（誰かが登録したライブを、ほかの人が探して使える）
- 申込状況の記録（Step2）、カレンダー連携（Step5）

## 3. 範囲

**作るもの**

1. **自分のライブ一覧のデータ**: ユーザーごとに「追加したライブ」を保存する（4.1）。
2. **ライブ一覧・次の締切の切り替え**: フォロー中の推しのライブではなく、自分のライブ一覧に入っているライブだけを出す。
3. **ライブを追加する画面**（2.1 の 4・5）
4. **追加と外す操作**: 検索結果とライブ詳細から追加でき、ライブ詳細から外せる（4.5）。
5. **登録・反映したライブを自動で追加**（4.4）
6. **ホームとライブ一覧のボタン・文言の変更**（4.9）
7. **セキュリティルール**と、そのテスト
8. **仕様書・DB 設計案の更新**（4.11。リーダーが行う）
9. **グッズ交換の手渡しの公演を、自分のライブ一覧の公演に合わせる**（4.7）

**作らないもの**

- 推しのフォローとライブの自動の結び付け（フォローしてもライブは追加しない）
- ライブの削除、重複したライブの統合（Step4 と同じく範囲外）
- グッズ交換の、手渡しの公演以外の変更（4.7）

## 4. 実装前に合意すること（合意済み: すべて推奨案）

**（合意済み 2026-11-06）** ユーザーが、この章の項目をすべて推奨案で確定した。リーダーはユーザーに確認せず、最初に `notes/判断ログ_A.md` へ「Step4.5 の実装前の合意（すべて推奨案。ユーザーが不在のため事前に確定）」として記録してから実装を始める。表の「推奨」は、そのまま決定として扱う。

### 4.1 自分のライブ一覧の保存場所

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **1（推奨）** | サブコレクション `users/{uid}/myLives/{liveId}`（項目は `addedAt`: サーバー時刻） | 1件ずつルールで検査できる。追加した日時を持てる。件数が増えても `users/{uid}` が大きくならない。申込状況（`applications`）と同じ作り | 一覧を読むときにクエリが1本増える |
| 2 | `users/{uid}` に配列 `myLiveIds` を持つ | 1ドキュメントで済む | ルールで要素の中身を検査できない。追加日時を持てない。件数の上限が要る |

- ドキュメント ID はライブの ID と同じにし、1ライブにつき1件とする（二重に追加されない）。

### 4.2 ライブ一覧・次の締切の読み方

- `users/{uid}/myLives` を購読して ID の集合を得る → その ID のライブを購読する（`FieldPath.documentId` の `whereIn`、30件ずつ分割）→ 公演・受付は `liveId` の `whereIn`（30件ずつ分割）で購読する。
- 結果のまとめ方は、Step2 の `_mergeQueries`（ID で重複を除き、どれかがエラーなら閉じる）と同じ規則にする。
- 自分のライブ一覧が空なら問い合わせない（空の `whereIn` はエラーになる）。
- 一覧に入っているのに読めないライブ（壊れたドキュメントなど）は飛ばす（Step2 と同じ）。
- 並べ方・「終了」の判定・次の締切の計算は、今の関数（`buildLiveList`・`upcomingDeadlines`）をそのまま使う。**入力を「フォロー中の推しのライブ」から「自分のライブ一覧のライブ」に替えるだけ**にする。

### 4.3 ライブを追加する画面

| 項目 | 推奨案 |
|---|---|
| ルート | `/lives/add`（`/lives` の子ルート）。**`:liveId` より前に置く**（後ろに置くと `add` がライブ ID として扱われる） |
| 推しの選び方 | 上部にフォロー中の推しをチップで並べ、1つ選ぶ（最初は先頭を選んだ状態）。「ほかの推しを探す」で、横山さんの `showPerformerPicker`（承認済みの推しから選ぶ）を使って、フォローしていない推しも選べる |
| ライブ名 | 任意の入力欄。入れると、選んだ推しのライブを正規化した名前（`normalizeName`）の部分一致で絞り込む |
| 探す範囲 | 選んだ推しがグループならそのグループのライブ、個人なら本人のライブと所属グループのライブ（今の `FollowTargets.fromFollowing([推し])` と同じ考え方）。今の `watchLives`・`watchPerformances` を流用できる |
| 推しを選ばずに名前だけで探す | **できないようにする**。Firestore では全ライブを名前で部分一致検索できず、全件を読むことになるため |
| 結果の並べ方 | 次の公演日が近い順。終わったライブは下に「終了」と表示（ライブ一覧と同じ関数を使う） |
| 結果の1行 | ライブ名、出演者、次の公演の日時・会場、公演数。右側に「追加」ボタン。追加済みなら「追加済み」と表示し、押すと外せる（確認なし） |
| 行を押したとき | ライブ詳細（`/lives/:liveId`）を開く。一覧に入っていないライブでも詳細は見られ、「ライブ一覧に追加」ボタンが出る |
| 見つからないとき | 「見つかりませんでした。右下の「ライブを登録する」から登録できます」 |
| フォロー中の推しがいないとき | 「推しをフォローするか、「ほかの推しを探す」から推しを選んでください」と、「推しを探す」（`/oshi/search`）へのボタン |
| 右下のボタン | 「ライブを登録する」→ `/register`（今と同じ） |

### 4.4 登録・反映したライブを自動で追加する

- **推奨: 自動で追加する。** 自分で登録したライブが自分の一覧に出ないと、登録した意味が分からなくなるため。
  - 新規作成（`LiveRepository.create`）: 同じ WriteBatch の中で `users/{uid}/myLives/{liveId}` も作る（ライブだけ作られて一覧に入らない、ということが起きない）。
  - 既存のライブに反映（Step4 の `applyMerge`）: 同じトランザクションの中で、そのライブを自分の一覧に追加する（既に入っていれば `addedAt` を変えない）。
  - 編集（Step4 の `/lives/:liveId/edit`）: 一覧から開くので、追加の処理は不要（入っていなければ追加する、でもよい）。
- `live_form_page.dart`（横山さんのファイル）は変えずに済む（リポジトリの中で書くため）。

### 4.5 一覧から外す

- ライブ詳細に「ライブ一覧から外す」を置く（確認ダイアログあり）。ライブを追加する画面の「追加済み」からも外せる。
- **外しても、申込状況（`applications`）は消さない。** もう一度追加すると、前の申込状況が戻る。
- Google カレンダーに追加済みの予定は、アプリからは消さない（Step5 の範囲。外したことは知らせない）。

### 4.6 一覧に入っていないライブの詳細

- 公演・受付・変更履歴は見られる（共通データ）。
- **申込状況の切り替えは出さず**、「ライブ一覧に追加すると、申込状況を記録できます」と表示する（一覧に入っていないライブの申込状況は、次の締切に出ないため）。
- 「このライブを編集」（Step4）は、一覧に入っていなくても使えるままにする（共通データの修正は誰でもできる、という Step4 の方針のため）。

### 4.7 グッズ交換も自分のライブ一覧に合わせる（合意済み）

- 横山さんの次の2か所が、フォロー中の推しのライブ（`livesProvider`・`performancesProvider`）を使っている。これを**自分のライブ一覧のライブ（`myLivesProvider`・`myPerformancesProvider`）に差し替える**。ユーザーが横山さんのファイルの変更を了承した。
  - `lib/features/trade/trade_post_form_page.dart`: 投稿の作成画面の「手渡しの公演」の候補
  - `lib/features/trade/board_filter_sheet.dart`: 掲示板の絞り込みの「手渡しの公演」
- 意味: 「自分が行く公演でだけ手渡しを選べる」「自分が行く公演で手渡しできる投稿を探せる」。
- 候補の計算（`handoverPerformanceCandidates`。対象の推しと今後の公演で絞る）は変えない。入力の公演を差し替えるだけにする。
- **候補が0件のとき**: 「この推しのライブを、ライブ一覧に追加すると選べます」と表示し、「ライブを追加する」（`/lives/add`）へのボタンを付ける（今の「対象の推しを選ぶと、今後の公演から選べます」は、推しを選ぶ前の表示として残す）。
- **一覧から外した公演が選ばれている投稿**: 編集画面で候補に出ないため、選択が見えないまま残る。「ライブ一覧に無い公演が n 件選ばれています」と表示し、「外す」で選択から外せるようにする（勝手には外さない）。
- 他人の投稿の手渡しの公演名は画面に出していない（確認済み）ので、表示の変更は要らない。
- **使われなくなる仕組みの削除**: 差し替えが終わったら、フォロー中の推しのライブを読むプロバイダ（`followTargetsProvider`・`livesProvider`・`performancesProvider`・`receptionsProvider`）がどこからも使われていないことを `grep` で確かめ、削除する（取り違えの防止）。`FollowTargets` クラスと `watchLives` などのリポジトリのメソッドは、ライブを追加する画面の検索で使うので残す。
- 横山さんのファイルで変えるのは上の部分だけ。ほかの部分（投稿の項目、掲示板の表示など）は変えない。変えた箇所はコミット案に書き、ユーザーが横山さんに伝える。

### 4.8 これまでのデータの扱い

- 切り替えると、これまでのテスト用のデータでは、全員のライブ一覧が空になる。
- **推奨: 移行はしない。** 今のデータはテスト用で、デモ用のデータは Step7 で作り直すため。必要なら、ライブを追加する画面から追加し直す。
- 比べた案: 初回だけ、自分が作成したライブ（`createdBy == uid`）や、申込状況があるライブを自動で追加する（処理とテストが増える）。

### 4.10 セキュリティルールの方針

| 対象 | 方針 |
|---|---|
| `users/{uid}/myLives/{liveId}` | 本人のみ読み書きできる。作成・更新は項目が `addedAt` だけで、`addedAt == request.time`。そのライブが存在すること（同じバッチで作る場合があるので `existsAfter`）。削除は本人なら可 |
| 広い `users/{uid}/{subcollection}` のルール | **`myLives` も除外する**（`applications` と同じ。ルールは OR で効くため、除外しないと上の検査が素通りになる） |
| `lives`・`performances`・`receptions` | 変えない（ログイン済みなら誰でも読める。ライブを追加する画面で探すために必要） |

- Step2・Step4 で実測した、ルールで別のドキュメントを読める回数の上限に注意する。新規作成のバッチに `existsAfter`（同じライブ）が1回増えるだけなので、上限に近い件数（公演50件・受付30件）で通るかを qa が確かめる。
- `firestore.rules` は横山さんと共有。Step4.5 で触るのは `users` の中の `myLives` と、広いルールの除外だけにする。デプロイは人間が行う。

## 6. 契約（インターフェース）

## 9. バグを防ぐための進め方

1. **担当外のファイルは編集しない。** 直してほしい箇所は担当者に SendMessage で伝える。
2. **契約を先に決める。** D1 が終わるまで、ui と qa は契約に依存する部分を書かない（画面の骨組みや、テストの準備は進めてよい）。
3. **各タスクの最初に、方針を3〜5行でリーダーに送る。** 特に最初のタスクは、リーダーの返事を待ってから書き始める。
4. **作業ツリーを壊れたまま放置しない。** 書きかけのコードで `flutter analyze` が通らない状態を長く残さない。
5. **品質ゲート:** タスクを完了にするたびに、`.claude/hooks/quality-gate.sh` が `flutter analyze`・`flutter test`・ルールのテストを実行する。失敗すると完了が差し戻される。
6. **仕様変更で落ちるテストは、7章の手順で qa が書き直す。** テストを消したり、期待を弱めたりして通さない。
7. **実装タスクを終えたら、qa にレビューを依頼する。** qa はレビュー依頼を最優先で処理し、指摘は担当者に SendMessage で返す。
8. **推測で決めず、実際に確かめる。** ルートの順番、ルールの上限など、動かせば分かることはテストやエミュレータで確かめてから決める。
9. **同じ判定を2か所に作らない。** 「追加済みか」「終了したか」は data の関数に一本化する。
10. **判断を記録する。** 比べた案・選んだ理由・捨てた案は、リーダーが `notes/判断ログ_A.md` に「Step4.5」として追記する。

## 10. レビューの観点

- 一覧・次の締切: フォローしただけで出ていないか。追加したライブだけが出るか。外すと消えるか。空の一覧で問い合わせていないか。30件を超えると分割しているか
- グッズ交換: 手渡しの公演の候補・掲示板の絞り込みが、自分のライブ一覧の今後の公演になっているか。候補0件の表示、一覧に無い公演が選ばれているときの表示。横山さんのファイルの、手渡しの公演以外の部分が変わっていないか。削除したプロバイダの使用箇所が残っていないか
- ライブを追加する画面: 推しを選ぶ前に全件を読んでいないか。個人の推しを選んだとき、所属グループのライブも出るか。ライブ名の揺れ（カタカナ・全角など）で見つかるか。追加ボタンの連打で二重に書かないか
- ルート: `/lives/add` がライブ詳細として扱われていないか（`:liveId` より前にあるか）。戻るボタンでホームに戻れるか
- 自動追加: 手入力・スクショ読み取り・既存への反映のどれでも、保存後に自分の一覧に入るか。ライブだけ作られて一覧に入らない状態が起きないか（同じバッチ・トランザクション）
- 申込状況: 外して追加し直すと、前の申込状況が戻るか。一覧に入っていないライブで申込状況を変えられないか
- ルール: 他人の `myLives` を読み書きできないか。`addedAt` の偽装、余計な項目、存在しないライブの追加が拒否されるか。広いルールで素通りしていないか
- `await` の後の `context.mounted`、Stream の購読の解除、処理中のボタンの無効化

## 11. ユーザーが行う動作確認

ルールを変えた後は、実際の Firestore で試す前に、人間が `firebase deploy --only firestore:rules` でデプロイする（`firestore.rules` は横山さんと共有なので、デプロイ前に一声かける）。

1. まだ使っていない Google アカウントでログインする → ホームは今までと同じ
2. 推しをフォローする → 「フォロー中の推し」には出るが、ライブ一覧と次の締切には何も出ない
3. ホームの右下が「ライブを追加する」になっている → 押すと、ライブを追加する画面が開く
4. フォロー中の推しを選ぶ → 誰かが登録したライブが出る。ライブ名を入れると絞り込まれる（カタカナ・全角でも見つかる）
5. 1件を「追加」→「追加済み」になる → ホームの次の締切と、ライブ一覧にそのライブだけが出る
6. ライブ詳細で申込状況を変える → 次の締切が切り替わる（今までどおり）
7. 「ライブ一覧から外す」→ 一覧と次の締切から消える。もう一度追加すると、申込状況が戻っている
8. 見つからない名前を入れる → 「見つかりませんでした」と出る → 右下の「ライブを登録する」→ 登録方法を選ぶ画面（今までと同じ）
9. 手入力で新しいライブを登録する → 保存後、自分のライブ一覧に入っている
10. 登録済みのライブを手入力・スクショで登録し、Step4 の照合で「既存に反映」→ そのライブが自分のライブ一覧に入る
11. 別のアカウントで同じ推しをフォロー → ライブ一覧は空のまま。ライブを追加する画面では、1つ目のアカウントが登録したライブが見つかる
12. グッズ交換の投稿画面で「手渡し」を選ぶ → 自分のライブ一覧に追加したライブの、今後の公演だけが候補に出る。一覧に無い推しを対象にすると「ライブ一覧に追加すると選べます」と出る
13. 手渡しの公演を選んだ投稿の、そのライブを一覧から外す → 投稿の編集画面で「ライブ一覧に無い公演が1件選ばれています」と出て、外せる
14. 掲示板の絞り込みの「手渡しの公演」も、自分のライブ一覧の公演から選べる

## 13. 使用量の上限・不在中の進め方

ユーザーは出かけていて、作業中は不在。使用量の上限に達すると、全員の作業が途中で止まる。上限が解除されると、見張り役のスクリプト（`.claude/scripts/auto-resume.sh`）が、リーダーの画面に「続けて」の指示を送る。**いつ止まっても、続きから再開できるように進める。**

### 13.1 進捗ファイル（いちばん大事）

- リーダーは `notes/step4_5_進捗.md` を、**タスクが1つ終わるたび**（完了・差し戻し・方針の決定のたび）に更新する。会話の記憶ではなく、このファイルを再開の手がかりにする。
- 書く内容は短く: タスクごとの状態（未着手・作業中・完了）、担当、触ったファイル、次にやること。迷った点やユーザーに聞きたいことは「帰宅後に確認すること」へ。
- チームメイトは、タスクを終えたら1〜2行の完了報告（タスクID、変えたファイル、残っていること）をリーダーに送る。リーダーがそれを進捗ファイルに書く。
- 全部終わったら、進捗ファイルの先頭を `状態: 完了` にする（見張り役は、これを見て止まる）。

### 13.2 再開の手順（「続けて」と言われたとき）

1. `notes/step4_5_進捗.md` と、この計画書の該当する章だけを読む（全体を読み直さない）。
2. `git status --short` で、作業ツリーに残っている変更を確かめる。
3. 共有タスクリストを確認する。チームメイトが残っていれば、止まっていた人に SendMessage で「進捗ファイルの続きから再開して」と送る。
4. Claude Code が再起動していてチームメイトがいない場合は、**まだ終わっていないタスクの担当だけ**を作り直す（12章の指示に「notes/step4_5_進捗.md を読み、自分の担当の未完了のタスクから再開すること」を足す）。完了済みのタスクはやり直さない。
5. 書きかけで `flutter analyze` が通らないファイルがあれば、まずそれを直してから先へ進む。

### 13.3 使用量を抑えるルール（全員）

- チームメイトのモデルは Sonnet。
- メッセージは短く。ファイルの中身やテストの出力を丸ごと貼らない（ファイル名と行番号、要点だけ）。
- テストは、作業中は関係するファイルだけを実行する（例: `flutter test test/utils/live_search_test.dart`）。全体の実行は、完了時の品質ゲートに任せる。
- 長い出力は末尾だけを見る（例: 出力の最後の40行）。
- 計画書は、自分の担当に関係する章だけを読み直す。
- 進み具合の確認のためだけのメッセージを送り合わない。待つときは、完了報告が届くのを待つ。
- リーダーはコードを1行ずつ読み直さない（レビューは qa に任せる）。

### 13.4 不在中の判断と、止まらないための注意

- **ユーザーに確認を求めて待たない。** 計画書に書いていないことで迷ったら、計画書の方針に沿った、元に戻しやすい控えめな方を選び、判断ログと進捗ファイルの「帰宅後に確認すること」に書いて先へ進む。
- 依存パッケージの追加、横山さんのファイルの範囲外の変更、ルールのデプロイ、コミット、push は、不在中は行わない（帰宅後に確認すること、に書く）。
- **許可の確認で止まらないように**、シェルのコマンドは1つずつ実行する（`;`・`&&`・`|` でつながない、`$変数` を使わない）。ファイルの読み書き・検索は、シェルではなく Read・Edit・Grep などの道具を使う。
- 作業ツリーを壊れたまま長く置かない（上限で止まると、そのまま残る）。大きな変更は、通る状態を保てる小さな単位に分ける。

### 13.5 非対話モード（`auto-resume-headless.sh`）で動くとき

tmux が使えないときは、`.claude/scripts/auto-resume-headless.sh` が Claude Code を非対話モード（`claude -p`）で繰り返し起動して進める。上限などで終了したら、20分待ってからまた起動する。

- **毎回が新しいセッション**で、会話の記憶は無い。進捗ファイル（`notes/step4_5_進捗.md`）と、この計画書だけを手がかりにする。
- agent team（チームメイト同士のメッセージ）は使えない。リーダーは、タスクを**1つずつサブエージェントに任せる**: data のタスクは `dev-data`、ui は `dev-ui`、qa は `dev-qa`（モデルは Sonnet）。指示には、計画書のパス、タスクID、担当ファイル、13.3 のルールを書く。
- 並行はしない（同じファイルの衝突を避けるため）。8章の依存関係の順に1つずつ進め、実装タスクの後には qa のレビュー（またはテストのタスク）を挟む。
- 1回の起動で全部を終わらせようとしない。**タスクが1つ終わるたびに進捗ファイルを更新する**（上限で突然止まるため）。
- 確認の画面は出ず、許可されていない操作は自動で断られる。断られたら、Read・Grep・Edit などの道具で行うか、「帰宅後に確認すること」に書いて先へ進む。
- 品質ゲート（タスク完了のフック）が動かないことがあるので、タスクを完了にする前に `flutter analyze` と、関係するテストを自分で実行して確かめる。最後に `flutter test` 全体とルールのテストを流す。
