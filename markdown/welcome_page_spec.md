# おしあし（仮）紹介ページ（ランディングページ） 仕様書

> 本ドキュメントは、ログインしていない人が最初に見る「紹介ページ」と、そこからログインへ進む流れの仕様書である。
> チームメンバーおよび開発支援に使う LLM が、同じ前提で作業するために使う。
> 「決定事項」と「未決定事項」を分けて記載している。

## 0. LLM への指示

- 本ドキュメントの「決定事項」は確定した仕様として扱うこと。
- 「8. 未決定事項」に挙げた項目は独自に確定させず、必ず「提案」として提示すること。
- 本仕様にない機能・作業（テストコードなど）を勝手に足さないこと。提案する場合は提案であることを明示すること。
- 開発は6章のステップの順に1つずつ進めること。各ステップの終わりに `flutter analyze` で問題がないことを確認し、1行程度の短いコミット文を添えること。
- コードの編集は人間が Dev Container（Docker コンテナ）内で行う。LLM はリポジトリを読むだけにして、変更はコードとして提示すること。
- 本ドキュメントや仕様書などの MD ファイルは、ユーザーの依頼なしに変更しないこと。

## 1. 概要

| 項目 | 内容 |
|---|---|
| 機能名 | 紹介ページ（ランディングページ） |
| 担当 | B（ルーターとログイン画面は A と共有してから触る） |
| 目的 | アプリを開いた人に、いきなりログインを求めず、まずアプリの内容を伝えてから「始める」でログインへ進んでもらう |
| ブランチ | 人間が作る（例：`features/welcome`） |

### 現状の問題

- ログインしていない人がアプリを開くと、説明のない「Google でログイン」のボタンだけの画面（`/login`）に移る。何のアプリかわからない。

### 利用の流れ

1. ログインしていない人がアプリ（どの URL でも）を開くと、紹介ページ（`/welcome`）が出る。
2. 紹介ページでアプリの内容を見て、「始める」を押すとログイン画面（`/login`）に移る。
3. ログイン画面で「Google でログイン」を押す。ログインできたら、これまでどおりホーム（初回はプロフィールの作成）に移る。
4. ログイン済みの人がアプリを開くと、紹介ページは出ず、そのままホームが出る。

## 2. 決定事項

### 2.1 ルートとリダイレクト

| パス | 画面 | ログインしていない人 | ログイン済みの人 |
|---|---|---|---|
| `/welcome` | 紹介ページ（新規） | 表示する | `/` へ移す |
| `/login` | ログイン画面（既存） | 表示する | `/` へ移す |
| 上記以外 | 既存の画面 | `/welcome` へ移す | これまでどおり |

- 判定は、これまでどおり `lib/app.dart` の `routerProvider` の `redirect` 1か所で行う。変えるのは「ログインしていない人の移動先（`/login` → `/welcome`）」と「ログインしていない人が見てよいパス（`/welcome` と `/login`）」だけとする。
- プロフィールの作成（未作成なら `/profile` へ）の判定は変えない。ログイン済みの人が `/welcome` を開いたときも、プロフィールが未作成なら `/profile` に移る。
- ログアウトしたときは、これまでの `/login` ではなく `/welcome` に移る（`redirect` の変更で自動的にそうなる）。
- 起動時のログイン状態の復元は、`main.dart` ですでに待っている（`authStateChanges().first`）。そのため、ログイン済みの人に紹介ページが一瞬見えることはなく、追加の対応は要らない。

### 2.2 紹介ページの内容

上から順に、次の4つの区画を縦に並べる。

| 区画 | 内容 |
|---|---|
| ① 見出し | アプリ名「おしあし」、キャッチコピー、ひとこと説明（1〜2行）、「始める」ボタン |
| ② 主な機能 | 3つの機能を、アイコン・見出し・説明（2行程度）で並べる |
| ③ 使い方 | 3ステップを、番号・見出し・説明で並べる |
| ④ 締め | ひとこと（例：「推し活の予定を、もう逃さない」）と、もう一度「始める」ボタン |

②の3つの機能は、プロジェクト仕様書の差別化ポイントとカレンダー連携とする。

| 機能 | 伝えること |
|---|---|
| スクショから読み取り | 告知画像やチケットサイトのスクショから、日程・申込期限・入金期限を自動で読み取る |
| みんなで共有 | 同じ推しの誰かが登録したライブ情報を、自分で入力しなくても使える（共通データ） |
| カレンダーと締切 | 公演・申込期限・入金期限を Google カレンダーに入れ、ホームで次の締切を確認できる |

③の3ステップは次のとおり。

| ステップ | 内容 |
|---|---|
| 1 | 推しをフォローする |
| 2 | ライブを追加する（スクショから読み取る、またはみんなが登録したライブから選ぶ） |
| 3 | カレンダーに入れて、申込・入金の期限を逃さない |

- 文言（キャッチコピー・説明）は、紹介ページのファイル内に定数としてまとめ、あとから直しやすくする。具体的な文言は W-2 で案を示して確認を取る。
- 画像は使わず、Material のアイコンだけで作る（画像の用意を待たずに作れるようにする）。
- 色・文字の大きさは、アプリのテーマ（`Theme.of(context)`）に従う。テーマ自体は変えない。

### 2.3 画面の幅への対応

- 内容の幅は最大 960px 程度とし、それより広い画面では中央に寄せる。
- 画面の幅が広いとき（目安 720px 以上）は、②の機能と③の使い方を横に3列で並べる。狭いとき（スマホ）は縦に1列で並べる。
- スマホの幅（360px）で、横にはみ出さないこと。

### 2.4 ログイン画面

- 「Google でログイン」のボタンと reCAPTCHA の文言（`login_recaptcha_notice`）は、文言・Key とも変えない（既存のテストのため）。
- 次のものを足す。
  - AppBar に戻るボタン。押すと紹介ページ（`/welcome`）に移る（URL を直接開いた場合もあるため、戻る履歴に頼らず `go` で移す）
  - ボタンの上に、アプリ名と短い説明（例：「Google アカウントでログインします。カレンダーへの追加は、あとで追加するときに許可を求めます」）

### 2.5 そのほか

- 紹介ページは Firestore を読まない（ログインしていない人はルールで読めないため）。
- 新しいパッケージは追加しない。

## 3. 画面構成

| 画面 | 内容 |
|---|---|
| 紹介ページ（新規） | 2.2 の4つの区画。「始める」で `/login` へ |
| ログイン画面（変更） | 戻るボタン、アプリ名と説明、「Google でログイン」、reCAPTCHA の文言 |

## 4. 非機能要件

- ログインしていない人は、`/welcome` と `/login` 以外の画面を開けない（これまでどおり、ルーターで移す）。
- ログイン済みの人に、紹介ページ・ログイン画面を見せない。

## 5. ファイル構成（予定）

| ファイル | 役割 |
|---|---|
| `lib/features/welcome/welcome_page.dart`（新規） | 紹介ページ |
| `lib/app.dart`（変更・A と共有） | `/welcome` のルートと、`redirect` の変更 |
| `lib/features/auth/login_page.dart`（変更・A と共有） | 戻るボタン、アプリ名と説明 |

## 6. 開発ステップ

| Step | 内容 | 状況 |
|---|---|---|
| W-1 | ルートとリダイレクト：`/welcome` を足し、ログインしていない人の移動先を `/welcome` にする（この時点の紹介ページは、見出しと「始める」だけの仮の画面でよい） | |
| W-2 | 紹介ページ：2.2 の4つの区画と、2.3 の画面の幅への対応。文言は案を示して確認を取る | |
| W-3 | ログイン画面：戻るボタン、アプリ名と説明 | |

W-1・W-3 は A の担当範囲（ルーター・ログイン画面）にかかわるため、着手前に A と共有する。

## 7. 確認すること（各ステップの終わりに画面で確認）

- ログアウトした状態で `/`・`/trade` などを開くと、`/welcome` に移る。
- 紹介ページの「始める」で `/login` に移り、ログイン画面の戻るで `/welcome` に戻る。
- ログインすると、ホーム（初回はプロフィールの作成）に移る。
- ログイン済みで `/welcome`・`/login` を開くと、`/` に移る。
- スマホの幅（360px）と PC の幅の両方で、表示が崩れない。
