## 4. 実装前に合意すること（提案）

リーダーは、次の項目を推奨案と理由つきでユーザーに示し、回答を `notes/判断ログ_A.md` に「Step7」として記録してから実装を始める。合意した項目は見出しに「（合意済み）」と付け、内容を書き換える。

### 4.1 当選者のみの受付の表示条件（合意済み。推奨案。カレンダーの追加シートは横山さんの了承あり）

- **条件**: そのライブ（`liveId`）の受付のどれかで、自分の申込状況が `won` または `paid` なら「当選者」とする。条件の判定は data の純粋関数1つにまとめる（Step6 の通知でも使う）。
- **見る場面では隠す**（推奨）:

| 場面 | 当選者 | 当選者でない人 |
|---|---|---|
| ホームの次の締切 | 出す | 出さない |
| ライブ詳細の受付一覧 | 出す（「当選者のみ」のラベル） | 出さない。代わりに「当選すると表示される受付が n 件あります」と1行だけ出す（存在は分かるようにする） |
| カレンダーの追加シート（横山さんのファイル） | 他の予定と同じく選べる | 出さない |

- **直す場面では隠さない**: Step4 の差分の確認・ライブの編集では、当選者でなくても `winnersOnly` の受付を表示する（隠すと、知らないうちに消したり重複させたりするため）。
- 当選者でなくなった（`won` → `lost` などに戻した）ら、すぐ隠れる（購読しているので自動で切り替わる）。
- カレンダーの追加シートは横山さんのファイル（`lib/features/calendar/calendar_add_sheet.dart`）。変えてよいかはユーザーが横山さんに確認する。了承が無ければ、シートは今のまま（当選者のみの予定は最初は選ばれていない）にする。

### 4.2 セキュリティルールの整備の進め方（合意済み）

1. **監査を先に**: qa が `firebase-security-rules-auditor` スキルで `firestore.rules` 全体を監査し、`notes/step7_ルール監査.md` に指摘を「重大／中／軽微」と、どのコレクション（誰の担当）かを付けて書く。
2. **直す範囲**:
   - A の担当（推し・ユーザー・申込状況・ライブ・公演・受付・履歴・自分のライブ一覧）は data が直す。
   - 横山さんの担当（グッズ・投稿・返信・チャット・メッセージ・プロフィール）は、**重大なものだけ**、ユーザーの了承を得てから data が直す。中・軽微は監査記録に残し、横山さんに渡す。
3. **テストを足す**: テストの無い横山さんのコレクションに、許可されるべき操作と拒否されるべき操作の基本的なテストを足す（ルールの中身は変えずに、今の動きを確かめるテスト）。
4. **インデックスの確認**: data が、アプリのすべてのクエリ（`where`・`orderBy`・`array-contains`・`whereIn` の組み合わせ）を洗い出し、複合インデックスが要るものが `firestore.indexes.json` にあるかを確かめる。足りなければ足す（デプロイは人間）。表にして `notes/step7_ルール監査.md` に残す。

### 4.3 ライブの大量作成への対策（合意済み: 案1。バッジの位置の追加指示あり）

### 4.4 デモ用データ（合意済み）

- **入れ方（推奨）**: Node.js のスクリプト（`tools/seed/`、Firebase Admin SDK）で入れる。推しの `status: approved` など、アプリからは書けない値も入れられる。
  - `node tools/seed/seed_demo.mjs --emulator` でエミュレータに、`--project oshiashi-test` で本番に入れる。`--delete` で消す。
  - ドキュメント ID は `demo-` で始まる固定の値にし、何度実行しても同じ内容に上書きされる（重複しない）。
  - **日時は実行した日を基準にずらす**（例: 申込期限は「2日後の23:59」、入金期限は「当日の5時間後」）。デモの撮影日に合わせて「期限が近い」状態を作れる。`--base 2026-11-09` で基準日を指定できる。
  - **認証情報はリポジトリに入れない**。本番に入れるときは、人がサービスアカウントの鍵をリポジトリの外に置き、`GOOGLE_APPLICATION_CREDENTIALS` で渡す（または `gcloud auth application-default login`）。
  - 入れたデータは、アプリから更新（Step4 の照合・編集）できる形にする（ルールの `hasOnly` に無い項目を足さない。`createdBy` などもそろえる）。
- **中身（推奨）**: すべて架空。
  - 推し: グループ1つ（例: 「ステラノート」）と、そのメンバー3人（例: 「星宮ルナ」など）、ソロの個人1人。
  - ライブ: 3件（今後のツアー、来月のフェス、終わったライブ）。公演はツアーに3件。
  - 受付: FC先行（申込期限が近い）、一般（申込開始前）、アプグレ（`winnersOnly`。入金期限が近い）、すでに当落が出た受付。
  - グッズ・投稿は入れない（横山さんの担当。必要なら横山さんと相談）。
- 告知画像（スクショ読み取りのデモ用）は、今回は作らない（人が架空の告知を用意する）。
- 動画では、シードしたデータであることを字幕などで明示する（デモ動画の偽装にならないように。ハッカソンのルール）。手順書に一言書く。

## 5. Step6（リマインド通知）を後で作るときのメモ

今回は作らない。Blaze に切り替えた後の指示書の土台にする。

- 方式: FCM の Web プッシュ。送信は Cloud Functions の定期実行（例: 15分おき）で、期限が近い受付を調べて送る。
- クライアント側（Blaze が無くても作れる部分）: 通知の許可の取得、FCM トークンの保存（例: `users/{uid}/fcmTokens/{token}`）、`web/firebase-messaging-sw.js`（サイトのルートに置く必要がある。4.5 の Hosting の設定で配信できるようにしておく）、アプリを開いているときの通知の表示、通知の設定画面。
- 送信側: 自分のライブ一覧（`myLives`）・申込状況・受付から「次の締切」を計算する。Dart の `nextDeadlineOf` と同じ規則を JavaScript で書くことになるので、両方に同じテストの例を用意する。当選者のみの受付は 4.1 の条件で絞る。
- 注意: iPhone は、ホーム画面に追加したとき（PWA）だけ Web プッシュが届く。デモは Android か PC の Chrome で行う。VAPID キーの作成と、Functions のデプロイは人が行う。

## 10. バグを防ぐための進め方

1. **担当外のファイルは編集しない。** 直してほしい箇所は担当者に SendMessage で伝える。
2. **契約を先に決める。** D1 が終わるまで、ui と qa は契約に依存する部分を書かない。
3. **各タスクの最初に、方針を3〜5行でリーダーに送る。** 特に最初のタスクは、リーダーの返事を待ってから書き始める。
4. **作業ツリーを壊れたまま放置しない。** 書きかけのコードで `flutter analyze` が通らない状態を長く残さない。
5. **品質ゲート:** タスクを完了にするたびに、`.claude/hooks/quality-gate.sh` が `flutter analyze`・`flutter test`・ルールのテストを実行する。失敗すると完了が差し戻される。
6. **仕様変更で落ちるテストは、8章の手順で qa が書き直す。** テストを消したり、期待を弱めたりして通さない。
7. **実装タスクを終えたら、qa にレビューを依頼する。** qa はレビュー依頼を最優先で処理する。
8. **推測で決めず、実際に確かめる。** ルールの挙動はエミュレータで、ビルドは `flutter build web` で、デモ用データはエミュレータに入れて確かめる。
9. **秘密情報を書かない。** reCAPTCHA のサイトキー、サービスアカウントの鍵、VAPID キーなどをリポジトリに書かない。設定の場所は手順書に書く。
10. **判断を記録する。** 比べた案・選んだ理由・捨てた案は、リーダーが `notes/判断ログ_A.md` に「Step7」として追記する。

## 11. レビューの観点

- 当選者のみ: 判定が1か所だけか。won・paid 以外（applied・lost・未申込）では隠れるか。別のライブの当選で見えてしまわないか。差分の確認・編集で隠れていないか。「n 件あります」の件数が合っているか
- ルール: 監査の重大な指摘が直っているか。直したことで既存のテストが落ちていないか。横山さんのコレクションのテストが、今の動きを正しく確かめているか（テストのために動きを変えていないか）
- インデックス: アプリのクエリのうち、複合インデックスが要るものがすべて `firestore.indexes.json` にあるか
- App Check（4.3 で採用したとき）: サイトキーがコードに書かれていないか。デバッグ用のプロバイダが本番のビルドで使われないか。初期化が `Firebase.initializeApp` の後で、ほかの Firebase の呼び出しより前か
- デモ用データ: 架空の名前だけか（実在の人物・団体・ロゴを使っていないか）。何度実行しても重複しないか。消すと完全に消えるか（サブコレクションの履歴も）。日時が基準日からの相対か。認証情報の扱い
- Hosting: 直接 `/lives/xxx` を開いても表示されるか（書き換えの設定）。キャッシュの設定。ビルドの警告
- `await` の後の `context.mounted`、処理中のボタンの無効化

## 12. ユーザーが行う動作確認と公開

ルール・インデックス・Hosting のデプロイは人間が行う（`markdown/deploy_手順.md` に従う。`firestore.rules` は横山さんと共有なので、デプロイ前に一声かける）。

1. アカウントAでライブを追加し、通常の受付とアプグレ（当選者のみ）の受付を入れる → アプグレは次の締切・ライブ詳細に出ず、「当選すると表示される受付が1件あります」と出る
2. 通常の受付を「当選」にする → アプグレが次の締切とライブ詳細に出る。「落選」に戻すと消える
3. ライブの編集・差分の確認では、当選していなくてもアプグレが見える
4. （4.1 で了承したとき）カレンダーの追加シートで、当選していればアプグレの予定も選べる
5. デモ用データをエミュレータに入れて、アプリ（ローカル）で表示を確かめる → 消すと完全に消える
6. `flutter build web --release` → プレビューの URL に公開 → 12章の公開後の確認（手順書）
7. （4.3 で採用したとき）App Check のコンソールで、公開したアプリからのリクエストが「検証済み」になっている

## 13. リーダー（メインセッション）の進め方

1. この文書と `CLAUDE.md` を読む。リーダーは自分でコードを書かず、調整・タスク管理・ユーザーへの確認・手順書の作成に専念する。
2. `git status -sb` で `feature/step6/7` にいて最新であることを確かめる（0章）。
3. `flutter analyze`・`flutter test`・ルールのテストを実行し、品質ゲートが通る状態かを確認する。通らなければ、原因をユーザーに報告して判断を仰ぐ。
4. 「4. 実装前に合意すること」を、項目ごとに推奨案と理由を付けてユーザーに示す。まとめて質問し、回答を判断ログに書き、4章を更新する。**合意するまでチームメイトは作らない。** 4.1 のカレンダーの追加シートと、4.2 の横山さんのルールの重大な修正については、横山さんの了承があるかもユーザーに聞く。
5. 依存パッケージ（`firebase_app_check` など）は、ユーザーの了承を得てからリーダーが追加する。
6. チームメイトを3人作る（**モデルは Sonnet**。使用量を抑えるため）。各チームメイトはリーダーの会話履歴を見られないので、作成時の指示に必要なことを書く。
   - `dev-data` エージェントタイプで、名前 `data`。指示: 「markdown/feature_step6_7_plan.md を読み、担当 data として D1 から始めて。D1 の方針を先に私（リーダー）に送ること。main.dart は App Check の初期化の数行以外を変えないこと。秘密情報を書かないこと」
   - `dev-ui` エージェントタイプで、名前 `ui`。指示: 「markdown/feature_step6_7_plan.md を読み、担当 ui として、D1 の契約が届くまでは U3（Hosting の設定とビルドの確認）から始めて。横山さんのファイルは、了承がある場合のカレンダーの追加シートの部分以外を変えないこと」
   - `dev-qa` エージェントタイプで、名前 `qa`。指示: 「markdown/feature_step6_7_plan.md を読み、担当 qa として T0 から始めて、次に Q2（ルールの監査）を。以降はレビュー依頼とテスト更新依頼を最優先に」
7. 9章のタスクを共有タスクリストに登録する（担当・依存関係つき）。
8. 進行中は、担当外ファイルの編集・同じファイルの同時編集・契約の食い違い・**横山さんのファイルへの想定外の変更**・**秘密情報の書き込み**・**テストを消して通していないか**を見張る。ユーザーが決めるべきことは、まとめてユーザーに聞く。
9. Q2 の監査で、横山さんのコレクションに重大な指摘があれば、直すかどうかをユーザーに聞く。
10. すべて完了したら L1 を行う。ユーザーに 12章の動作確認手順と、コミット案（メッセージと含めるファイル、横山さんのファイル・共有ファイルを変えた箇所）を示し、了承を得てからコミットする。`git push`・Pull Request・デプロイはユーザーが行う。
11. 最後にチームメイトを終了させ、チームを片付ける。

## 14. 使用量の上限で止まったときのために

- リーダーは `notes/step6_7_進捗.md` を、**タスクが1つ終わるたび**に更新する（状態・担当・触ったファイル・次にやること）。止まって再開するときは、まずこのファイルを読み、終わったタスクはやり直さない。
- Claude Code が終了してチームメイトがいなくなったら、まだ終わっていないタスクの担当だけを作り直す（13章の指示に「notes/step6_7_進捗.md を読み、自分の未完了のタスクから再開すること」を足す）。
- 使用量を抑えるルール（全員）: メッセージは短く、ファイルの中身やテストの出力を丸ごと貼らない。作業中のテストは関係するファイルだけを実行し、全体は完了時の品質ゲートに任せる。長い出力は末尾だけを見る。計画書は自分に関係する章だけを読み直す。進み具合の確認のためだけのメッセージを送り合わない。
- 許可の確認で止まらないように、シェルのコマンドは1つずつ実行する（`;`・`&&`・`|` でつながない、`$変数` を使わない）。ファイルの読み書き・検索は Read・Edit・Grep などの道具を使う。
